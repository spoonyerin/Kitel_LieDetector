## 1. 한 줄 요약

PPG(심박·맥파), GSR(피부 전기 반응), FSR(손가락 압력) 변화를 개인 기준값과 비교해 진실/거짓을 판정하고, **왜 그렇게 판정했는지 이유**까지 웹사이트에 보여주는 생체신호 기반 거짓말탐지 게임.

## 2. 기획서 요약

### 제작 동기 (기존 거짓말탐지기 장난감의 한계)

1. 단일 생체신호 중심 (GSR만 사용)
2. 단순한 결과 출력 (변화 과정 분석 없음)
3. 단순하거나 제한적인 촉각 피드백 (진동 또는 전기충격)
4. 개인별 생체신호 차이 미반영 (판정값이 고정됨)

### 제작 목표

여러 생체신호를 측정해 **개인별 기본값을 기준으로 변화 양상을 분석**하여 판정하는 시스템.

### 동작 4단계

1. **안정 상태 측정**: 손을 올리고 안정 상태의 생체신호를 측정한다.
2. **질문 및 답변**: 질문에 답하는 동안 생체신호 변화를 측정한다.
3. **진실/거짓 판정**: 안정 상태 대비 변화를 분석하고 다중 신호의 변화 패턴을 종합해 판정한다.
4. **게임형 결과 피드백**: 판정 결과를 확인한다 (기획서: 앱 + 거짓 판정 시 저주파 촉각 피드백).

## 3. 기획서 대비 변경 사항

| 항목 | 기획서 | 현재 (이 문서) |
|---|---|---|
| 결과 확인 | 앱 (플랫폼 미정) | **웹사이트** |
| 촉각 피드백 | 저주파 마사지기 + 릴레이 2개 | **LED + OLED**로 대체. 마사지기는 가능할 때만 하는 선택 사항 |
| 판정 위치 | ESP32가 판정 후 앱으로 전송 | 실험 단계는 **PC(Python)에서 판정을 설계·검증**하고, 검증 후 ESP32로 옮긴다 (`INTEGRATION.md`와 같은 방향) |
| 기기와 PC 연결 | BLE/Wi-Fi 중 선정 | **현재 LieDetector 방식: PC가 COM 포트로 기기의 출력을 읽는다.** 서버도 같은 COM 포트를 읽기 전용으로 읽는다 (`SOURCE=serial`). 블루투스인지 USB인지는 확인 필요 |
| 실험 질문 | 숫자 카드 등 통제된 질문 | **LieDetector의 질문 은행 15문항** (연습 1 + 본 질문 5, 순서 섞기) |

그 외 센서 3종, 개인 기준값 방식, 전처리, 특징값, 로지스틱 회귀 계획은 기획서와 같다.

## 4. 현재 시스템의 실제 동작 (LieDetector 코드와 실험 로그에서 확인)

- **기기가 게임 진행을 주도한다.** 물리 버튼으로 진행하고, 로그에서 확인된 흐름은 다음과 같다.
  `PLACE_HAND`(손 올리기) → 버튼 → `BASELINE`(기준 측정) → `READY` → 버튼 → `QUESTION` → 버튼 → `RESPONSE`(답변, 시간 제한) → `ANALYZING` → `RESULT` → 버튼(짧게: 다음 질문, 길게: 세션 종료)
- 손 접촉은 FSR로 감지한다 (`HAND_OK`, `HAND_LOST`). 접촉 문제는 `CONTACT_DIP`, `CONTACT_SHIFT`, `CONTACT_BACK` 이벤트로 알려 준다.
- 기기는 50Hz로 샘플을 내보내고, 기준과 시험이 끝날 때 요약(`#BASELINE`, `#SUMMARY`)을 보낸다. 요약에는 유효 여부, 사유, 기준 대비 z-score(`fsr_dz`, `gsr_dz`)가 들어 있다.
- **PC는 읽기만 한다.** `record_session.py`는 기기로 아무것도 보내지 않는다.
- PC의 수집기는 참가자 ID와 "거짓으로 답할 질문 번호"를 받아 질문을 고르고 섞고, 라벨(진실/거짓)을 숨겼다가 세션 후 확인 단계에서 실제 답변을 확정한다. 저장 시 시간 간격, 순번, 접촉, 포화 등의 무결성을 검사한다.
- **미확인 (펌웨어 소스 필요):** 기기가 LED/OLED에 참/거짓을 어떤 기준으로 표시하는지, 연결이 블루투스인지 USB인지.

### 목표

|---|---|

- 의료, 법적 증거, 채용 등 실제 판단 용도. **오락(게임) 목적**이며 화면에도 명시한다.
- 정확도 수치를 보장하는 주장.
- 클라우드 서버, 다중 사용자 계정, 앱스토어 앱.
- 센서 사양 변경 (PPG, GSR, FSR 3종 고정).

## 6. 사용자와 시나리오

- **참가자**: 센서에 손가락을 올리고 질문에 답하는 사람
- **진행자**: 기기 버튼을 누르고 질문을 읽어 주는 사람

### 게임 모드

1. 진행자가 서버를 켜고 웹을 연다. 참가자 별칭을 입력한다 (서버 내부에서만 사용).
2. 참가자가 센서에 손을 올리고 기기 버튼으로 세션을 시작한다 (기기 주도).
3. 웹은 기기가 보내는 단계(기준 측정, 질문, 답변, 분석, 결과)를 따라간다. 질문 문장은 서버가 질문 은행에서 보여 준다.
4. 답변이 끝나면 서버가 판정하고, 웹에 결과와 이유를 표시한다.
5. 다음 질문과 종료는 기기 버튼으로 한다.

### 실험 모드 (데이터 수집)

기존 `collector/record_session.py` 방식을 그대로 쓴다. 판정 결과는 참가자에게 보여주지 않고, 정답 라벨은 판정 입력에 절대 들어가지 않는다.

## 9. 판정과 이유

### 전처리 (시작값, LieDetector 분석 코드 기준)

| 센서 | 처리 |
|---|---|
| FSR | 5샘플 중앙값 필터 + 5Hz 저역통과 |
| GSR | 5샘플 중앙값 필터 + 1Hz 저역통과 |
| PPG | 0.5~5Hz 대역통과 (초기 실험용 범위) |

기획서는 이동평균과 저역통과(`butter`, `filtfilt`)를 검토한다고 했다. 실시간 경로에서는 앞뒤를 모두 보는 `filtfilt`를 쓰지 않는다.

### 특징값 (기획서 + LieDetector 분석 코드)

| 센서 | 특징 |
|---|---|
| PPG | 심박 변화량, 최대 변화, 반응 지속시간, 맥파 진폭 변화 |
| GSR | 기준 대비 변화량, 최대 변화량, 반응 지속시간 |
| FSR | 압력 변화량, 최대 변화, 변동 정도 |
| 공통 | 기준 평균/중앙값/표준편차/범위, 답변 구간 평균 변화, 최대 변화, 변동 정도, 기기 요약의 `fsr_dz`, `gsr_dz` |

처음에는 6개 안팎으로 시작한다. 표준편차 하한과 z-score 클리핑 정책을 정한다. 20초 구간에서 안정적인 HRV는 가정하지 않는다.

현재 판정에 쓰는 특징은 **국소 dz** 두 개(FSR, GSR)뿐이다: 같은 시도의 (답변 구간 평균 − 질문 구간 평균) / 기준 표준편차(하한 적용). 기기 요약의 `fsr_dz`, `gsr_dz`는 세션이 길어질수록 한 방향으로 커지는 추세가 있어 표시용으로만 쓴다. IR로 추정한 심박수는 화면 표시용이며 판정에 쓰지 않는다.

### 판정 모델

기획서대로 **로지스틱 회귀**로 거짓일 점수(0~1)를 계산하고 임계값(예: 0.5)과 비교한다. 데이터가 모이기 전에는 규칙 판정기를 쓴다: |국소 dz| ≥ 3.0σ인 센서가 1개 이상이면 거짓. 3.0σ는 통계 관례로 정한 값이며 라벨 데이터로 맞추거나 검증하지 않았다. 규칙 판정기는 점수를 내지 않는다(`score=null`). 확률 보정을 평가하기 전에는 "확률"이라고 부르지 않고 "거짓 점수"라고 한다.

### 판정 결과 형식

```json
{
  "type": "trial_result",
  "source": "dummy | hardware",
  "session_id": "20261104_S01_1",
  "participant_id": "1",
  "trial_id": 3,
  "question_id": "Q02",
  "decision": "truth | lie | inconclusive",
  "score": null,
  "judge": { "name": "rule | logreg", "version": "0.0.1", "trained": false },
  "judge_note": "규칙 판정 임계값(FSR 3.0σ, GSR 3.0σ, 1개 센서 이상)은 통계에서 흔히 쓰는 관례로 정한 값이며, 라벨 데이터로 맞추거나 검증하지 않았습니다.",
  "quality": { "ok": true, "flags": [], "warnings": [] },
  "features": { "fsr_local_dz": -3.71, "gsr_local_dz": -2.77, "fsr_dz": -4.35, "gsr_dz": -1.67 },
  "contributions": [
    { "sensor": "fsr", "feature": "fsr_local_dz", "value": -3.71, "contribution": 1.24, "direction": "down", "over_threshold": true }
  ],
  "reasons": ["답변 중 손가락 압력(FSR)이 질문 구간보다 3.7σ 낮았습니다 (임계값 3.0σ)."],
  "hold_reason": null,
  "hold_code": null,
  "disclaimer": "오락용 게임입니다. 이유는 통계적 설명이며 거짓의 증명이 아닙니다.",
  "device_verdict": null
}
```

- 보류이면 `hold_reason`에 쉬운 문장(예: "손 위치가 바뀌어 이 답변은 측정에서 제외했어요."), `hold_code`에 코드(예: `CONTACT_EVENT:CONTACT_SHIFT`)가 들어간다.
- `session_id`는 현재 서버가 세션 순번(`S01`, `S02`)으로 채우고, `participant_id`, `question_id`는 null이다 (참가자 입력과 질문 표시 미구현).

- `device_verdict`는 기기가 자체 판정 결과를 PC로 보내는 경우에만 채운다 (현재 로그에는 없음).
- `trained=false`이면 웹에 "모델 미학습(데모)" 배지를 항상 표시한다.
- 품질 불량이면 `decision`은 `inconclusive`, `score`는 null이다.
- 이유는 통계적 설명이지 거짓의 증명이 아니라는 안내를 화면에 둔다.

## 10. 데이터 정책

- 모든 기록에 `source`(`dummy` 또는 `hardware`)를 붙인다. 더미는 `data/dummy/`에만 저장하고 학습이 읽지 못하게 한다.
- 원시 신호(IR, Red, GSR, FSR)를 요약값과 함께 보관한다.
- 참가자는 별칭만 쓰고 실명, 연락처를 저장하지 않는다. 실험 전에 측정 목적과 데이터 사용에 대한 동의를 받는다.
- 실측 데이터(`data/`)는 GitHub에 올리지 않는다.
- 라벨은 기존처럼 세션 후 확인 단계에서 실제 답변을 확인해 확정한다 (`planned_condition`과 `condition` 구분).
- 현재 학습에 쓸 수 있는 데이터는 0건이다. I1(정상 시도가 ABORTED로 처리됨)은 현재 수집기 코드에서 재현되지 않지만, 기존 기록은 모두 연습 질문이라 라벨이 없다.
- 현재 서버는 받은 기록을 저장하지 않는다 (저장 위치 미정, development.md I6). 데이터 수집은 수집기로 한다.

## 11. 성공 기준

### 시연 기준

- 기기 버튼으로 진행하는 한 사이클(기준 → 질문 → 답변 → 판정)이 웹에 **연속 10회 중단 없이** 표시된다.
- 접촉 불량이면 오판 대신 "보류"가 표시된다.
- 학습되지 않은 판정기(`trained=false`)일 때 "모델 미학습(데모)"가 항상 보인다.

### 모델 기준 (데이터 확보 후)

- 참가자 단위로 분리한 검증에서 "항상 다수 클래스로 예측"하는 기준 모델보다 균형 정확도가 높다.
- 거짓 검출률과 진실을 거짓으로 오판하는 비율을 함께 보고한다.
- 위 기준을 못 넘으면 학습 모델을 채택하지 않고 규칙 판정기로 시연한다.
- 목표 정확도 수치는 데이터를 본 뒤 정한다.

## 12. 위험과 대응

| 위험 | 영향 | 대응 |
|---|---|---|
| 라벨이 있는 본 질문 데이터 0건 (I1은 현재 코드에서 재현 안 됨) | 모델 학습 불가 | 짧은 실제 세션으로 라벨이 남는지 확인 후 수집 (M1) |
| 규칙 판정기 임계값(3.0σ)과 심박 추정값이 검증되지 않음 | 판정·표시가 틀릴 수 있음 | 화면에 미검증 안내, 라벨 데이터와 다른 측정기로 검증 |
| 펌웨어 소스가 없음 | 기기 판정·표시 방식을 알 수 없음 | 담당자에게 소스 요청 |
| 로그에 ESP32 재부팅(`Guru Meditation Error`) 1건 | 수집 중단 | 펌웨어 확인 시 원인 분석 |
| 모델 성능이 우연 수준 | 학습 모델 사용 불가 | 규칙 판정기와 이유 설명 중심으로 시연 |
| 참가자 모집 지연 | 데이터 부족 | 더미 기반 개발과 수집을 병행 |
| 웹 판정과 기기 LED 판정의 불일치 | 혼란 | F11에서 일치 방안 결정 |
| 개인차, 움직임, 접촉 노이즈 | 오판 | 개인 기준값, 품질 검사, 보류 판정 |

기획서 일정표 기준으로 11월은 디버깅과 발표 준비 기간이다. 최종 발표일은 미정이며 확정되면 아래에 날짜를 붙인다.

## 14. 미결 사항

1. 최종 발표(품평회) 날짜
2. 펌웨어(KITEL_MAIN_V5) 소스와 담당자
3. 기기가 LED/OLED에 참/거짓을 어떤 기준으로 표시하는지
4. 기기와 PC 연결이 블루투스인지 USB인지 (코드는 COM 포트를 읽으므로 동작에는 영향 없음)
5. LED 개수/색, OLED 모델, 핀 배정
6. 웹의 참가자 입력과 질문 표시 방식 (기기에는 질문 문장이 없으므로 서버가 질문 순서를 가져야 함)
7. 실험 참가자 수와 일정
8. 저주파 마사지기 사용 여부

## 15. 용어

| 용어 | 뜻 |
|---|---|
| PPG | 광학식 맥파. 심박 계산에 사용 |
| GSR | 피부 전기 반응 (피부전도도) |
| FSR | 힘 감지 저항. 손가락 압력과 손 접촉 감지에 사용 |
| 기준값(baseline) | 안정 상태에서 측정한 개인별 평균과 표준편차 |
| z-score (σ, dz) | 현재 값이 개인 기준에서 표준편차의 몇 배만큼 벗어났는지 |
| 보류(inconclusive) | 신호 품질이 나빠 판정하지 않는 결과 |
| 더미 / 실측 | 합성 신호 / 센서로 측정한 신호 (`source`로 구분) |
