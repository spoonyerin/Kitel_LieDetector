# TruthPulse PRD (제품 요구사항 문서)

- 버전: 0.1 (초안)
- 작성일: 2026-11-04
- 작성: 유예린 (Claude 보조)
- 상태: 더미 데이터로 기능을 먼저 구현하고, 실측 데이터가 모이면 판정 모델을 교체하는 방식으로 진행

---

## 1. 한 줄 요약

손가락을 올리고 질문에 답하면 심박(PPG), 피부 전기 반응(GSR), 손가락 압력(FSR)의 변화를 개인 기준값과 비교해 진실/거짓을 판정하고, **왜 그렇게 판정했는지 이유까지** 웹, LED, OLED로 보여주는 생체신호 기반 거짓말탐지 게임.

## 2. 배경과 문제

기존 거짓말탐지기 장난감의 한계:

1. GSR 하나만 쓰는 단일 신호 중심
2. 결과만 출력하고 변화 과정 분석이 없음
3. 촉각 피드백이 단순하거나 제한적임 (진동 또는 전기충격)
4. 개인별 기본값 차이를 반영하지 않고 판정값이 고정됨

TruthPulse는 여러 신호를 개인 기준값 대비 변화량으로 분석하고, 판정 근거를 사용자에게 설명한다는 점이 차별점이다.

## 3. 목표와 비목표

### 목표

| ID | 목표 |
|---|---|
| G1 | PPG, GSR, FSR을 동시에 측정하고 개인 안정 상태 기준 대비 변화로 판정한다. |
| G2 | 판정 결과와 **판정 이유**를 웹 화면에 보여준다. |
| G3 | 장치 자체의 LED와 OLED로도 결과(진실/거짓/보류)를 보여준다. |
| G4 | 판정기를 교체 가능한 구조로 만들어, 더미 판정기에서 학습 모델로 코드 변경 없이 바꿀 수 있게 한다. |
| G5 | 실측 데이터와 더미 데이터를 항상 구분해 저장하고, 더미 데이터는 학습에 쓰지 않는다. |

### 비목표

- 의료, 법적 증거, 채용 등 실제 판단 용도. **오락(게임) 목적**이며 화면에도 이를 명시한다.
- 정확도 수치를 보장하는 주장. 거짓말 탐지는 생체신호만으로 정확도가 높지 않은 것으로 알려져 있다.
- 클라우드 서버, 다중 사용자 계정, 앱스토어 앱.
- 센서 사양 변경 (현재 PPG, GSR, FSR 3종 고정).

### 변경된 사항 (중간발표 대비)

| 항목 | 중간발표 | 현재 |
|---|---|---|
| 결과 출력 | 앱 + 저주파 촉각 피드백 | 앱(웹) + **LED + OLED** |
| 저주파 마사지기 | 필수 | **선택(Optional)**. 제어 가능 여부가 불투명해 후순위 |
| 앱 | 플랫폼 미정 | 웹(브라우저) |

그 외 센서, 판정 흐름, 개인 기준값 방식은 중간발표 계획과 같다.

## 4. 사용자와 시나리오

- **참가자**: 센서에 손가락을 올리고 질문에 답하는 사람
- **진행자**: 질문을 읽어 주고 웹 화면을 조작하는 사람 (참가자와 같은 사람일 수도 있음)

### 기본 흐름

1. 진행자가 웹에서 장치를 연결하고 참가자 별칭을 입력한다.
2. **안정 상태 측정(기준값)**: 참가자가 손가락을 올리고 약 15초 가만히 있는다.
3. **질문 제시**: 질문이 웹에 표시된다. 그 뒤 약 20초의 답변 구간 동안 신호를 측정한다.
4. **판정**: 기준값 대비 변화로 진실/거짓/보류를 판정하고 이유를 만든다.
5. **결과 표시**: 웹 결과 카드, 장치 LED, 장치 OLED에 같은 결과를 동시에 보여준다.
6. 다음 질문으로 넘어가거나 세션을 종료한다.

(15초, 20초는 현재 수집기 기준값이며 센서 반응 확인 후 조정할 수 있다.)

### 실험(데이터 수집) 모드

위 흐름과 같지만, 질문마다 정답 라벨(진실/거짓)을 기록하고 **판정 결과를 참가자에게 보여주지 않는다**. 라벨은 판정 입력에 절대 들어가지 않는다.

## 5. 기능 요구사항

|---|---|---|---|
| F1 | P0 | 세션 제어 (연결, 기준 측정 시작, 질문 시작, 취소, 새 세션) | 웹 버튼으로 한 사이클을 끝까지 진행할 수 있고, 취소하면 중간 결과가 판정으로 이어지지 않는다. |
| F2 | P0 | 신호 수집 | ESP32 시리얼 50Hz 샘플(FSR, GSR, IR, Red, contact)을 서버가 받아 저장한다. 순번, 시간 역전, 끊김을 검사한다. |
| F3 | P0 | 품질 검사 | 접촉 불량, 결측, 포화, 끊김이 있으면 판정하지 않고 "보류"와 사유를 표시한다. |
| F4 | P0 | 개인 기준값 | 안정 구간 초반 불안정 구간을 제외하고 센서별 평균과 표준편차를 계산한다. 변화 없는 평평한 신호는 거부한다. |
| F5 | P0 | 특징 추출 | 답변 구간에서 센서별 특징값을 계산한다 (7절 참고). 정답 라벨은 사용하지 않는다. |
| F6 | P0 | 교체식 판정기 | 더미, 규칙, 학습 모델이 같은 입출력 형식을 가진다. 설정 한 줄로 교체된다. |
| F7 | P0 | 판정 이유 생성 | 판정마다 센서별 기여도와 한국어 이유 문장을 만든다. 보류일 때는 보류 사유를 만든다. |
| F8 | P0 | 웹 결과 화면 | 판정, 이유, 센서별 변화 그래프, 최근 20초 신호를 표시한다. 더미 판정기일 때 "모델 미학습(데모)" 배지를 항상 띄운다. |
| F9 | P0 | LED, OLED 출력 | 8절의 표대로 상태와 결과를 장치에 표시한다. 장치가 없을 때는 웹의 가상 장치 패널이 같은 동작을 보여준다. |
| F10 | P1 | 기록과 내보내기 | 모든 기록에 source(`dummy` 또는 `hardware`)를 남긴다. CSV 요약과 JSON 원본을 내보낼 수 있다. |
| F11 | P1 | 더미/재생 모드 | 하드웨어 없이 (a) 합성 신호, (b) 저장된 `raw_serial_log.txt` 재생으로 전체 흐름이 동작한다. |
| F12 | P1 | 학습 파이프라인 | 실측 라벨 데이터로 모델을 학습하고 `model.json`으로 내보낸다. 참가자 단위로 분리해 검증한다. |
| F13 | P2 | 저주파 피드백 | 거짓 판정 시 릴레이로 마사지기를 제어한다. 제어 가능성이 확인될 때만 진행한다. |
| F14 | P2 | 질문 은행 관리 | 질문 목록을 웹에서 확인하고 고른다. |

## 6. 하드웨어 구성

| 구분 | 부품 | 비고 |
|---|---|---|
| 제어 | ESP32 DevKitC | 센서 수집, 서버 통신, LED/OLED 제어 |
| 입력 | MAX30102 (PPG) | I²C, 3.3V |
| 입력 | Grove GSR | 아날로그, ADC |
| 입력 | FSR 402 | 전압분배 회로, 아날로그 |
| 출력 | LED | 색과 개수는 확인 필요 (초록, 빨강, 노랑 3색 또는 RGB 1개) |
| 출력 | OLED | I²C. 모델 확인 필요 (SSD1306 계열이면 주소 0x3C) |
| 선택 | 릴레이 2개 + HDW-300 | 저주파 피드백. 가능 여부 불투명 |

확인할 사항: MAX30102(보통 0x57)와 OLED의 I²C 주소가 충돌하지 않는지, LED와 OLED 핀 배정이 기존 센서 핀과 겹치지 않는지.

## 7. 판정과 이유

### 판정 결과 형식

모든 판정기는 같은 형식으로 결과를 돌려준다.

```json
{
  "type": "trial_result",
  "source": "dummy | hardware",
  "session_id": "20261104_S01_1",
  "participant_id": "1",
  "trial_id": 3,
  "question_id": "Q02",
  "decision": "truth | lie | inconclusive",
  "score": 0.72,
  "judge": { "name": "dummy | rule | logreg", "version": "0.0.1", "trained": false },
  "quality": { "ok": true, "flags": [] },
  "features": { "gsr_dz": 2.3, "fsr_dz": -0.4 },
  "contributions": [
    { "sensor": "gsr", "feature": "gsr_dz", "value": 2.3, "contribution": 0.8, "direction": "up" }
  ],
  "reasons": ["피부전도(GSR)가 평소보다 2.3σ 높았습니다. 가장 큰 판정 요인입니다."],
  "hold_reason": null
}
```

규칙:

- `judge.trained`가 false이면 웹에 "모델 미학습(데모)" 배지를 표시하고, score를 "확률"이라고 부르지 않는다. 학습 후 확률 보정을 평가하기 전까지도 "거짓 점수"라고 부른다.
- 품질 불량이면 `decision`은 `inconclusive`, `score`는 null, `hold_reason`에 사유를 넣는다.
- `ground_truth`는 실험 기록에만 저장하고 판정 입력에는 넣지 않는다.

### 특징값 후보 (처음에는 약 6개로 시작)

| 센서 | 특징 | 비고 |
|---|---|---|
| PPG | 심박수 변화 (IR 피크 기반) | 20초 구간에서 안정적인 HRV는 가정하지 않는다. |
| PPG | 맥파 진폭 변화 | |
| GSR | 최대 변화, 반응 면적 | 회로 보정 전에는 물리 단위를 가정하지 않는다. |
| GSR | 기준 대비 z-score (`gsr_dz`) | 펌웨어 요약에 이미 있음 |
| FSR | 평균 변화, 변동 정도 | 거짓 신호보다 접촉/움직임 품질 정보로 더 유용할 수 있어 비교한다. |
| FSR | 기준 대비 z-score (`fsr_dz`) | 펌웨어 요약에 이미 있음 |

표준편차가 작을 때 z-score가 과도하게 커지므로 표준편차 하한과 이상치 처리 정책을 정한다.

### 이유 생성 규칙

1. 센서별 기여도 = 모델 계수 × 표준화한 특징값 (규칙 판정기는 임계 초과량).
2. 판정 방향(거짓 쪽 또는 진실 쪽)에 기여한 상위 2~3개를 고른다.
3. 템플릿으로 문장을 만든다. 예: "{센서 이름}이(가) 평소보다 {값}σ {높았/낮았}습니다."
4. 어떤 판정기든 이 단계는 동일하게 동작한다.
5. 이유는 "이 변화가 거짓과 관련 있었다"는 통계적 설명이지 거짓의 증명이 아니라는 안내를 화면에 둔다.

## 8. 장치 출력 (LED, OLED)

색상 배정은 제안이며 부품 확인 후 확정한다.

| 상태 | LED | OLED (영문 기본) |
|---|---|---|
| 대기, 연결됨 | 노랑 느리게 깜빡임 | `READY` |
| 기준 측정 중 | 노랑 점등 | `BASELINE` + 남은 시간 |
| 답변 측정 중 | 노랑 빠르게 깜빡임 | `ANSWER` + 남은 시간 |
| 진실 | 초록 3초 | `TRUTH` |
| 거짓 | 빨강 3초 | `LIE` |
| 보류 (접촉 불량 등) | 노랑 2회 깜빡임 | `RETRY` + 짧은 사유 코드 |
| 오류, 연결 끊김 | 빨강 느리게 깜빡임 | `ERROR` |

OLED 한글 표시는 폰트 용량 문제가 있으므로 영문과 숫자를 기본으로 하고, 한글 표시는 선택 사항이다. 한글 이유 문장은 웹에서 보여준다.

## 9. 데이터 정책

- 모든 기록에 `source`를 붙인다. 더미 데이터는 별도 폴더에 저장하고 학습 파이프라인이 읽지 못하게 한다.
- 원시 신호(IR, Red, GSR ADC, FSR ADC)를 파생값과 함께 보관한다. 전처리를 다시 검증할 수 있어야 한다.
- 참가자는 별칭(P01 등)만 쓰고 실명, 연락처를 저장하지 않는다. 실험 전에 측정 목적과 데이터 사용에 대한 동의를 받는다.
- 실측 데이터는 GitHub에 올리지 않는다 (`.gitignore` 처리). 공유가 필요하면 별도 저장소나 압축 파일로 한다.
- 질문 후 확인 단계에서 참가자가 실제로 어떻게 답했는지 확인해 라벨을 확정한다 (기존 수집기 동작 유지).

## 10. 성공 기준

### 시연 기준

- 장치 연결 → 기준 측정 → 질문 → 판정 → 이유 표시를 **연속 10회 중단 없이** 수행한다.
- 접촉 불량 시 오판 대신 "보류"가 표시된다.
- 웹, LED, OLED의 결과가 항상 일치한다.
- 더미 판정기 상태에서 "모델 미학습(데모)"가 항상 보인다.

### 모델 기준 (데이터 확보 후)

- 참가자 단위로 분리한 검증에서 "항상 다수 클래스로 예측"하는 기준 모델보다 균형 정확도가 높다.
- 거짓 검출률과 진실을 거짓으로 오판하는 비율을 함께 보고한다.
- 위 기준을 못 넘으면 학습 모델을 채택하지 않고 규칙 판정기로 시연한다 (예비안).
- 목표 정확도 수치는 데이터를 본 뒤 정한다. 지금은 약속하지 않는다.

## 11. 위험과 대응

| 위험 | 영향 | 대응 |
|---|---|---|
| 정상 질문이 ABORTED로 처리되어 학습 가능 데이터가 0건 | 모델 학습 불가 | M1에서 최우선 수정 |
| 모델 성능이 우연 수준 | 학습 모델 사용 불가 | 규칙 판정기와 이유 설명 중심으로 시연 |
| 참가자 모집 지연 | 데이터 부족 | 더미 기반 개발을 병행하고 수집은 일찍 시작 |
| 저주파 마사지기 제어 불가 | 촉각 피드백 없음 | LED/OLED로 대체 (이미 반영) |
| 펌웨어 소스가 저장소에 없음 | LED/OLED 코드 수정 곤란 | 펌웨어(KITEL_MAIN_V5)를 `firmware/`에 추가 |
| I²C 주소/핀 충돌 | 센서 또는 OLED 동작 불량 | 부품 확인 후 핀맵 문서화 |
| 생체신호의 개인차, 움직임, 접촉 노이즈 | 오판 | 개인 기준값, 품질 검사, 보류 판정 |

|---|---|
| M0 | 저장소, 폴더 구조, 문서 세팅 |
| M1 | 수집기 라벨 버그 수정, 실측 수집 시작 (이후 계속 병행) |
| M2 | 서버, 재생기, 더미 판정기, 이유 생성 (명령줄에서 먼저 확인) |
| M3 | 웹 연결 (WebSocket), 가상 LED/OLED 패널 |
| M4 | 펌웨어 LED/OLED 출력, 서버→ESP32 결과 명령 |
| M5 | 규칙 판정기 (예비안) |
| M6 | 학습 파이프라인, 학습 모델 교체 (데이터 충분 시) |
| M7 | 통합 테스트, 리허설, (선택) 저주파 피드백 |

## 13. 미결 사항

1. 최종 발표(품평회) 날짜
2. LED 종류와 개수, OLED 모델과 해상도, 핀 배정
3. 펌웨어 소스 위치 (현재 첨부된 폴더에는 수집기 Python 코드만 있음)
4. 판정을 최종적으로 PC 서버에서 할지 ESP32로 이식할지 (현재 계획은 서버 판정 후 결과를 장치로 전송)
5. 실험 참가자 수와 일정
6. 저주파 마사지기 사용 여부

## 14. 용어

| 용어 | 뜻 |
|---|---|
| PPG | 광학식 맥파. 심박 계산에 사용 |
| GSR | 피부 전기 반응 (피부전도도) |
| FSR | 힘 감지 저항, 손가락 압력 |
| 기준값(baseline) | 안정 상태에서 측정한 개인별 평균과 표준편차 |
| z-score (σ) | 현재 값이 개인 기준에서 표준편차의 몇 배만큼 벗어났는지 |
| 보류(inconclusive) | 신호 품질이 나빠 판정하지 않는 결과 |
| 더미 / 실측 | 합성 신호 / 센서로 측정한 신호 (`source`로 구분) |
